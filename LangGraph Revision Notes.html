LangGraph Revision Notes

Agents, Memory, and 6 types of RAG. Simple English, interview ready.

1. What is an Agent?

Simple definition: An agent is an LLM that decides what to do next, uses tools, and keeps looping until the task is finished.

  • Chain: steps are fixed by the developer. Agent: the LLM chooses the steps.
  • The loop (ReAct = Reason + Act): Think, then Act (call a tool), then Observe (read the result), then repeat. Stop when it can give the final answer.
  • 4 parts of an agent: LLM (brain), Tools (search, SQL, API, calculator), Memory (what happened so far), Instructions (system prompt).

In LangGraph an agent is a graph with a loop:

  • State: shared data passed between steps (usually the list of messages).
  • Node: a function that does work (agent node calls the LLM, tools node runs tools).
  • Edge: a fixed arrow from one node to the next.
  • Conditional edge: picks the next node by checking the state. Example: tool calls present, go to tools. No tool calls, go to END.
  • Shortcut: create_react_agent builds this whole loop for you.
Example: User asks “Weather in Pune today? Do I need an umbrella?”
  • LLM thinks: I need live data, so it calls the weather tool.
  • Tool returns: 80 percent chance of rain.
  • LLM reads the result and answers: “Yes, carry an umbrella.”

Works well when: the steps are not known in advance (research, support bots, data lookups with several tools).

Avoid when: the steps are always the same. Use a simple chain or workflow, it is cheaper and more predictable.

Interview answer: “An agent is an LLM in a loop with tools. It reasons, calls a tool, reads the result, and repeats until done. In LangGraph I model it as a graph with an agent node, a tools node, and a conditional edge that decides to continue or stop.”

2. Memory in LangGraph

LLMs forget everything between calls. LangGraph gives two kinds of memory.

Short-term memory (Checkpointer)

  • Remembers the state of one conversation (thread).
  • Saved automatically after every step as a checkpoint.
  • Identified by thread_id passed in config: {"configurable": {"thread_id": "1"}}.
  • Savers: InMemorySaver (testing), SqliteSaver, PostgresSaver (production).
  • Bonus powers: resume after a crash, human-in-the-loop pause, time travel to an old checkpoint.

Long-term memory (Store)

  • Remembers facts across threads and sessions.
  • Data is saved as JSON under a namespace (like a folder, e.g. (user_id, "memories")) and a key.
  • Methods: put, get, search. Examples: InMemoryStore, Postgres store.
  • Connect both: graph.compile(checkpointer=..., store=...).

3 kinds of long-term memory:

  • Semantic: facts (name, city, preferences).
  • Episodic: past experiences (what worked last time).
  • Procedural: rules and instructions (how the agent should behave).

Long chat problem: the message list grows and exceeds the context window. Fix by trimming old messages, summarizing them, or deleting them (RemoveMessage). The state field uses a reducer like add_messages so new messages are appended, not overwritten.

Example: In thread 1 the user says “My name is Pradip”. Later in thread 1 the bot remembers (checkpointer). In a new thread 2 it does not, unless the name was saved in the Store under that user’s namespace.

Works well when: Checkpointer for chat history, approvals, and recovery. Store for user profile, preferences, and learned facts.

Interview answer: “Checkpointer is short-term memory, scoped to one thread_id. Store is long-term memory, shared across threads, organized by namespace and key.”

3. Types of RAG

Normal RAG: question, retrieve top chunks from a vector DB, LLM answers from them. It is one shot and cannot fix bad retrieval. Each type below solves a specific weakness.

A. Agentic RAG

  • An agent decides whether to retrieve, which source to use, rewrites the query, checks the results, and retries if they are poor.
  • Retriever is just a tool the agent can call.
Example: HR bot gets “Leave rules for contract staff in Pune?” Agent searches, sees only general policy, rewrites the query with “contract” and “India”, searches again, then answers.

Works well when: questions are vague or need several tries, or there are many sources.

Avoid when: simple FAQ. Extra LLM calls add cost and delay.

B. Multi-Agent RAG

  • Several specialist agents, each with its own tools and data source, coordinated by a supervisor. A writer agent combines the outputs.
Example: “Compare our Q3 sales with competitor news.” SQL agent gets sales numbers, Web agent gets news, Docs agent gets internal strategy notes. Writer agent builds one report.

Works well when: the answer needs different kinds of data (SQL, PDFs, web) and each needs its own skill.

Avoid when: one source is enough. More agents means more cost and harder debugging.

C. Autonomous RAG

  • Agentic RAG with more freedom: the system makes a plan, breaks it into sub-goals, retrieves again and again, reflects on whether it has enough, saves notes in memory, and stops by itself.
  • Think “deep research” mode. The term is used loosely in industry, so state your definition in the interview.
Example: “Write a market report on EV batteries in India.” System plans 5 sub-questions, researches each, notices a gap in pricing data, researches again, then writes the report.

Works well when: open-ended, long tasks with no fixed path.

Avoid when: you need predictable cost, speed, or strict control. Add step limits and human approval.

D. Cache RAG

Two meanings, know both:

  • CAG (Cache-Augmented Generation): load the whole knowledge base into the LLM context once and reuse its KV cache. No retrieval step at question time.
  • Semantic cache: store past question and answer pairs. If a new question is similar, return the saved answer without calling the LLM.
Example: (A) A 40-page product manual fits in the context, so the support bot preloads it. (B) Many users ask “How do I reset my password?”, so the saved answer is returned instantly.

Works well when: CAG for small, stable knowledge. Semantic cache for repeated questions.

Avoid when: CAG with a large or fast-changing knowledge base. Semantic cache when answers go stale quickly.

E. Adaptive RAG

  • A router checks how hard the question is, then picks the cheapest strategy that works: no retrieval, single retrieval, or multi-step retrieval.
Example: “Hello” goes straight to the LLM. “What is the refund policy?” does one retrieval. “How did the refund policy change over the last 3 years and why?” runs a multi-step loop.

Works well when: traffic mixes easy and hard questions and you want to save cost and time.

Avoid when: all questions are similar. The router adds its own cost and can misjudge.

F. VectorLess RAG

  • Retrieval without embeddings or a vector DB. Uses keyword search (BM25), SQL, knowledge graphs, or a tree index of a document where the LLM reads section titles and summaries and walks to the right section (for example PageIndex).
Example: Question on a 200-page annual report: “What is the liquidity risk?” LLM opens Finance, then Liquidity, reads only that section, and answers. No chunking or embedding needed.

Works well when: long structured documents (reports, legal, manuals), exact terms matter, you want explainable retrieval, or you want no embedding cost.

Avoid when: huge messy collections of unrelated documents, or when meaning-based search is needed (“similar idea, different words”).

Last-minute Interview Lines

  • Agent vs chain: chain has fixed steps, agent chooses steps.
  • Checkpointer vs Store: per-thread short-term vs cross-thread long-term.
  • Agentic vs Multi-Agent: one agent with tools vs many specialist agents.
  • Agentic vs Autonomous: Autonomous has more planning, reflection, and self-control.
  • Adaptive vs Agentic: Adaptive routes by question difficulty. Agentic reasons and loops inside a question.
  • Why VectorLess: avoids chunking loss and embedding cost on structured documents.
  • Always mention: trade-off between answer quality, cost, and latency.
